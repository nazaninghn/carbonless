# "I don't know — answer later": which questions may be deferred

Generated from the questionnaire catalogue (`nexus.../src/lib/carboniq/questions.js`) by
`nexus.../scripts/generate-deferral-policy.mjs` into `questionnaire/deferral_policy.json` (server) and
`src/lib/carboniq/deferralPolicy.js` (frontend); this document is written from that policy by
`nexus.../scripts/generate-answer-later-doc.py`. Never edit the three by hand: change the generator (its
`--check` mode, run by `npm run test:unit`, fails when a copy differs). The same route
walk runs in `questionnaire/deferral.py` and `src/lib/carboniq/deferral.js`; `deferral_parity.json` (generated by
`nexus.../scripts/generate-deferral-parity.mjs`, `--check` in `npm run test:unit`) pins them together. Nothing in this policy calculates anything or stores an answer.

## The rule, by what a question DOES

| Class | Meaning | "Answer later" |
|---|---|---|
| **A · REQUIRED** | Its answer routes the questionnaire (any `nextByValue`: yes/no gates, summary confirmations), defines what later questions are about (loop sources, facility count), sets the organizational boundary or the calculation method / data source, identifies the inventory, or is the sign-off. Per-item answers of a loop are required at item level (`loop_item`): the loop's source question defines the items. | never offered; the server refuses it |
| **B · DEFERRABLE** | Profile details, documentation and data inputs that change neither the route, the boundary nor the method. | offered; saves **no** answer (not even 0) |
| **C · CONDITIONAL** | On the route only for some answers (a follow-up of a "yes", a question that exists for one boundary approach ...). Once it applies it is REQUIRED or DEFERRABLE as shown. | offered only while it applies; once the answers take it off the route it is inactive: not pending, not counted |
| — info | Information screens and section pickers: not questions. | n/a |

"Applies" is decided by the questionnaire's own route (the answers given so far), evaluated on the server. A new
deferral is accepted only for a question on the **confirmed** route (up to the first gate that is still
unanswered); a question beyond an unanswered gate is not applicable yet.

Counts (178 questions): required: 33, deferrable: 10, conditional>deferrable: 49, info: 12, conditional>required: 74.

## Question 36 (`SCOPE-GROUPING`) — "How would you like to answer the Scope 1 and Scope 2 questions?"

**REQUIRED.** It is read at the point where Scope 1 hands over to Scope 2 (`3-GİRİŞ` → `4-GİRİŞ`): `separate` shows the
Scope 2 introduction as its own section, anything else skips it. So the answer chooses the route of the questionnaire.
Deferred, the route was silently taken as "together" — an answer nobody gave. It is also carried to the next year's
inventory as a boundary/structure choice (`CARRY_STEPS`). It is therefore not deferrable.

## What the server enforces

* `POST /api/questionnaire/<id>/pending/` refuses a question that is not deferrable (`400 not_deferrable`, with the
  reason code and a bilingual message) or does not apply (`409 not_applicable`).
* The status payload lists only pending questions that still apply (unanswered and on the route).
* Marking the inventory complete is refused while a deferred question is unanswered (`pending_questions`) or a
  required question on the route is unanswered (`required_unanswered`).

## How the classification is verified (scripts/audit-route-graph.mjs, part of `npm run test:unit`)

The questionnaire has 48 branching questions (107 branches), 43 conditionally shown questions, 23 loop questions and
4 section pickers; the naive space of answers is about 2^53. A route only depends on the answers a later question still
*reads*, so the audit walks every reachable (question, still-read answers, visited cycle members) state with
memoization (about 1,300 states, under a second). It uses the engine's own `nextQuestionId` and
`conditionalShowMatches`. It proves, over **every** route of a user who answers what is shown:

* which questions are always / sometimes / never on the route, and that this equals the policy's classification;
* that no route dead-ends (every route ends at the sign-off 7B-INFO or the end of the assumptions review 6B-5);
* that every answer of every branching question and every satisfiable condition is reachable (branch coverage);
* that every question that can be hidden has a default route to go to when it is;
* that the engine's walk equals the explorer's on 20,000 random routes and on a witness route for every claim.

Systematic witnesses (a route that avoids each conditional question, every boundary value of every condition
source, 60 complete routes) are added to `deferral_parity.json`, which both the JavaScript and the Python engine must
reproduce, together with the confirmed route, the pending list, the required-unanswered list and every deferral decision.

**Findings of the audit:** (1) the sampling used to classify the questions had treated conditional gates as always
asked (2B-OC1, 2B-FC1, 3C-0) and the assumptions review (6B-2..6B-5) as always on the route; they are conditional
and now classified so. (2) A real routing defect: K3C14-0 had no default route, so for a company without
franchises the skip found nowhere to go and the questionnaire announced "All questions completed" after category 13.
It now continues to category 15.
(3) 22 `conditionalShow` rules are implied by the route itself (the question can only be reached through the matching
answer); they never hide it and are harmless.

**Limits (documented, not hidden):** answers are modelled as options (compound answers by representative values per
condition outcome, boundaries included) and a user is assumed to answer what the route shows, so the exhaustive
search does not enumerate the four situations below. They are covered by their own tests
(`questionnaire/test_deferral_edge_cases.py`) and behave as follows.

* **Answers left on an abandoned branch.** Changing a gate never deletes the answers behind it: they stay saved and
  come back, unchanged, when the gate is changed back. They are off the route, so they are not counted as pending,
  not required, and they do not reach a calculation (the existing gate rules in `step_entries.py` already ignore
  them). A pending mark on an inactive question is kept but not shown and does not block completion.
* **Editing a saved answer.** The server decides everything from the saved answers by the route they give: a
  changed gate that opens a required question makes the sign-off refuse with the list of those questions
  (`required_unanswered`); a change that opens nothing is not blocked; no other answer is touched; the inventory is
  never marked complete by an edit.
* **Loops without items.** A loop with no items is skipped by the questionnaire and by the server alike, so its
  per-item questions are not pending and block nothing; they are never enforced by `required_unanswered` (the loop
  source is). With items, an old mark on a per-item question is still enforced. `loopSources` and the `ls`/`lio`
  fields of the policy let the server tell (a port of `buildLoopItems`; a doubt is resolved towards "has items").
* **The workspace chat.** It has no write path into the questionnaire: it only reads answers to reply, the guided
  mode of `ChatWorkspace.jsx` (not mounted anywhere) keeps its answers in component state and never sends them.
